### 3.4 缓存分析（关键）

| | 配置 A (直接) | 配置 B (AgentLab) |
|--|-------------|------------------|
| 对 `agent_registry.yml` 的处理 | 读 1 次，后续在上下文中引用 | Supervisor 读 1 次；RepoScout 又读 1 次；TesterAuditor 又读 1 次；Archivist 又读 1 次（重复 4 次） |
| 对 `index.html` 的处理 | 读 1 次 | RepoScout 读 1 次；InterfaceMapper 又读 1 次；Coder 又读 1 次；TesterAuditor 又读 1 次（重复 4 次） |
| 对 Supervisor 报告的处理 | 推理中直接使用 | 生成 → 写入磁盘 → 后续 6 个 agent 各读 1 次（多占用 6×1,800 = 10,800 tokens） |

**AgentLab 的"衔接成本"就是重复读取：相同的文件被 4-7 个 agent 各自独立读取，没有任何共享缓存。**

### 为什么 AgentLab 不节省 token？

**根本原因：AgentLab 的 7 个 agent 各自是独立的 API 调用，互不共享上下文。**

在直接模式下，我（外部 AI）做一次推理就把 Supervisor+RepoScout+InterfaceMapper+Coder+TesterAuditor+Archivist 都完成了——所有文件只读一次，所有推理共享同一个 token 上下文。

AgentLab 要做同样的事：
1. Supervisor 输出路由计划 → 写入文件
2. RepoScout 读文件 + 读 Supervisor 报告 → 输出仓库报告 → 写入文件
3. InterfaceMapper 读文件 + 读前两份报告 → 输出接口报告 → 写入文件
4. ...（重复 7 次）

每多一次调用，就多一次 System Prompt（~800 tokens），多一次读报告文件（~1,200-8,500 tokens），而这些在直接模式中都是隐式存在于单次推理中的。

**AgentLab 的 token 模型适用于什么场景？**

| 场景 | AgentLab token 优势？ |
|------|---------------------|
| 外部 AI 直接在单个对话中完成 | ❌ AgentLab 多 24% token |
| 跨 session（第二天继续） | ✅ agent_docs 持久化，外部 AI 需要重新读全部文件 |
| 纯 API 模式，无外部 AI | ✅ 可以分散到多个小调用（绕过最大 context 限制） |
| 需要精确控制每个阶段的输入 | ✅ 每个 agent 输入量可控 |
